## The idea

Once data is copied to several machines, the copies can disagree for a while: a write reaches one replica before the others, or the network between them breaks. Every distributed database decides what to do in that moment. Interviewers ask about CAP to see whether you can make that choice for a specific feature and explain it.

## CAP in plain terms

- **Consistency (C)**: every read sees the most recent write, as if there were only one copy.
- **Availability (A)**: every request to a working node gets an answer (not an error).
- **Partition tolerance (P)**: the system keeps running when the network splits nodes into groups that can't talk.

Networks do fail, so P isn't optional for a system spread over machines. The real statement is: **during a partition, choose C or A.**

- **CP**: refuse or delay requests that can't be answered correctly. Right for balances, seat booking, inventory and anything where a wrong answer costs money.
- **AP**: answer from whatever copy you can reach and reconcile later. Right for feeds, likes, view counts, shopping-cart contents and presence ("online now").

Choose **per feature**, not per company. The same app can keep payments CP and the activity feed AP.

## Consistency levels

From strongest to weakest, the ones worth naming:

| Level | What the user sees | Example use |
| --- | --- | --- |
| Strong (linearizable) | Always the latest write | Wallet balance, seat booking |
| Read-your-writes | Always their own latest writes; others' may lag | Editing your own profile |
| Monotonic reads | Never older data after newer data | Scrolling a timeline without items vanishing |
| Eventual | All copies agree once writes stop, usually within seconds | Like counts, view counts |

Weaker levels are faster and stay available; stronger levels cost coordination between replicas on every operation.

## Quorums

Leaderless stores such as Cassandra and DynamoDB let you tune this per request. With **N** copies, a write waits for **W** acknowledgements and a read asks **R** replicas.

- If **R + W > N**, the read set and write set always overlap, so a read sees the latest write. With N = 3, W = 2 and R = 2 is the usual balanced choice.
- **W = 1, R = 1** is fastest and most available, but reads can be stale.
- Larger W makes writes slower and more fragile; larger R does the same for reads.

## PACELC

CAP only talks about partitions. **PACELC** adds the everyday case: if there is a **P**artition, choose **A** or **C**; **E**lse, choose **L**atency or **C**onsistency. Even on a healthy network, waiting for a second replica to confirm costs a round trip. Many systems pick low latency in normal operation and accept brief staleness.

## What interviewers look for

- **A correct statement of CAP**: the choice is C or A during a partition, not "pick any two".
- **Per-feature decisions** with reasons tied to the cost of a wrong or missing answer.
- **Concrete mechanisms**: quorums, read-your-writes, leader-based replication.
- **Latency awareness**: strong consistency across regions means cross-region round trips on every write.

## Common mistakes

- **"We'll choose CA."** A system on more than one machine can't opt out of partitions.
- **One consistency level for the whole product**, usually the strongest, paying its cost everywhere.
- **Calling eventual consistency "data loss".** Nothing is lost; copies converge.
- **Forgetting the user's own writes**, so people can't see what they just posted.
