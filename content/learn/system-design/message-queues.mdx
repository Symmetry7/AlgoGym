## The idea

Some work doesn't need to finish before you reply to the user: sending an email, resizing an uploaded photo, updating a search index, generating an invoice PDF. Put a message describing the work on a **queue**, reply at once, and let **workers** process the queue in the background.

## What a queue buys you

- **Faster responses.** The user waits for the database write, not the email provider.
- **Absorbing spikes.** When Tatkal booking opens at 10 a.m., requests arrive far faster than downstream systems can process them. The queue grows, workers drain it at a steady rate, and nothing falls over.
- **Decoupling.** The checkout service doesn't know or care who listens. Adding a new consumer (say, a loyalty-points service) needs no change to checkout.
- **Retries.** If a worker fails, the message is still in the queue and can be tried again.

## Delivery guarantees

| Guarantee | Meaning | Cost |
| --- | --- | --- |
| At most once | Never duplicated, may be lost | Simple; fine for metrics you can afford to drop |
| At least once | Never lost, may be duplicated | The common default; consumers must handle duplicates |
| Exactly once | Neither | Only within limited setups, and expensive; usually approximated |

Because of **at least once**, consumers must be **idempotent**. Give each message an ID, record the IDs you've processed (or use a database constraint), and skip repeats. Charging a card twice because a message was redelivered is the bug interviewers are looking for you to prevent.

## Retries and dead letters

Retry failed messages with **exponential backoff** (wait 1 s, 2 s, 4 s, 8 s…) and a little random jitter, so a struggling dependency isn't hammered. After a fixed number of failures, move the message to a **dead-letter queue** and alert someone. A bad message should never block the line.

## Queue or log

- **Job queues** (RabbitMQ, Amazon SQS): each message goes to one worker and is deleted once acknowledged. Good for tasks.
- **Logs** (Kafka, Redpanda): messages are appended to a partitioned log and kept for days. Each consumer group reads at its own position and can replay. Good for event streams that several systems consume, such as order events feeding notifications, analytics and search.

In a log, order is guaranteed only **within a partition**, so give related events the same partition key (for example the order ID) when their order matters.

## Writing to the database and the queue together

If the app writes the order and then crashes before publishing the event, the email never goes out. If it publishes first and the write fails, a customer gets an email for an order that doesn't exist. The **outbox pattern** fixes this: write the event into an `outbox` table in the same database transaction as the order, and have a separate process publish rows from the outbox to the queue.

## What interviewers look for

- **Spotting async work.** Anything slow, unreliable or not needed for the response moves off the request path.
- **Idempotent consumers** and a stated delivery guarantee.
- **Failure handling.** Retries with backoff, a dead-letter queue, and monitoring of queue length.
- **The right tool.** A job queue for tasks, a log for shared event streams, with a reason.

## Common mistakes

- **Making the user wait on a queue**, such as publishing a job and then polling for its result inside the same request.
- **Assuming exactly-once delivery** and writing non-idempotent consumers.
- **Unbounded retries** that loop forever on a bad message.
- **No one watching queue depth.** A queue that grows all day means workers can't keep up; scale them or alert.
