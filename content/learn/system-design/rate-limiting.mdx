## The idea

A rate limiter caps how many requests a client may make in a period, such as 100 a minute per API key. It protects the service from abusive bots, scrapers, password-guessing and the honest bug in someone's retry loop, and it keeps one heavy customer from starving everyone else.

The client is identified by whatever is most reliable: an API key or user ID for signed-in traffic, an IP address for anonymous traffic (with care, since many users can share one IP behind a college or office network).

## Algorithms

| Algorithm | How it works | Notes |
| --- | --- | --- |
| Fixed window | Count requests per calendar minute; reset at the boundary | Simple; allows a double burst around each boundary |
| Sliding window log | Store each request's timestamp; count those in the last 60 s | Exact; memory grows with traffic |
| Sliding window counter | Weighted mix of this window's and the last window's counts | Close to exact with two numbers per client |
| Token bucket | Tokens refill at a steady rate up to a cap; each request takes one | Allows short bursts, enforces the average; very common |
| Leaky bucket | Requests queue and leave at a fixed rate | Smooths output; adds waiting |

The **token bucket** is a good default to name. Its two settings map to product language: the bucket size is the burst you tolerate, the refill rate is the sustained limit.

## Where it lives

<ArchDiagram id="limiter" />

- **At the edge** (API gateway, load balancer or CDN): rejects bad traffic before it costs you anything. The usual place.
- **In each service**, for limits only that service understands, such as "5 OTP requests per phone number per hour".
- **On the client**: polite, but never trusted. A client can be modified.

With many gateway servers, counters must be **shared**. Keep them in Redis and update them atomically (a Lua script, or `INCR` with an expiry), so a check-and-decrement can't race. A Redis round trip costs well under a millisecond in the same data centre. If Redis is unavailable, decide in advance whether to **fail open** (allow traffic, protecting availability) or **fail closed** (block it, protecting the backend); most public APIs fail open.

## Telling the client

Reply **429 Too Many Requests** with a `Retry-After` header. Many APIs also send headers such as `X-RateLimit-Remaining` so well-behaved clients slow down before they hit the wall. Clients should retry with exponential backoff and jitter, not in a tight loop.

## What interviewers look for

- **Clarifying the limit**: per user, per key, per IP or per endpoint, and what happens when it is exceeded.
- **A named algorithm with its trade-off**, usually token bucket or sliding window.
- **Distributed counting**: shared, atomic counters, and a stated fail-open or fail-closed choice.
- **Placement**: at the edge first, with service-specific limits where needed.

## Common mistakes

- **Per-server counters** behind a load balancer, which multiply the real limit by the number of servers.
- **Read-then-write counters** without atomicity, so two requests both see "99" and both pass.
- **Limiting by IP alone**, blocking a whole hostel behind one address while a bot with many IPs walks through.
- **Returning 500 or 503** instead of 429, so clients can't tell overload from being limited.
