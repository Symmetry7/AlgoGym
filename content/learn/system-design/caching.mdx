## The idea

A cache keeps a copy of data somewhere faster than where it really lives, usually in memory and usually closer to the user. A Redis lookup takes well under a millisecond; the database query it replaces might take 5 to 50 ms and use up a connection the database can't spare. Most products read the same small slice of data over and over, so a modest cache absorbs most of the read traffic.

Caching works when data is **read much more than it is written** and **a little staleness is acceptable**. Say both conditions out loud when you add one.

## Where caches sit

From the user inwards:

1. **Browser cache**, controlled by `Cache-Control` headers.
2. **CDN**: servers in many cities that keep copies of images, scripts and even whole pages near users. A user in Chennai gets the file from a Chennai or Bengaluru edge instead of from your origin in Mumbai or abroad.
3. **Application cache**: Redis or Memcached shared by all app servers, holding query results, sessions and computed values.
4. **Database cache**: the database's own memory buffer for hot pages and indexes.

## Reading and writing

**Cache-aside (lazy loading)** is the default. The app checks the cache; on a miss it reads the database and fills the cache. Only data that is actually requested gets cached, and if the cache dies the app still works, just slower.

When data changes, you have choices:

| Strategy | On a write | Trade-off |
| --- | --- | --- |
| Invalidate (delete the key) | Write the database, then delete the cache key | Simple and safe; the next read pays for a miss |
| Write-through | Write the cache and the database together | Reads are always warm; every write is slower |
| Write-back (write-behind) | Write the cache now, the database later | Fast writes; data is lost if the cache dies first |

With cache-aside, deleting the key after writing the database is usually better than updating it, because two concurrent updates can otherwise leave the older value in the cache.

## Expiry and eviction

- **TTL (time to live)**: every entry expires after a set time, say 5 minutes. It caps how stale data can get, even if an invalidation is missed. Pick it per data type: seconds for stock levels, hours for a user's profile picture.
- **Eviction**: when memory is full, something has to go. **LRU** (least recently used) is the usual choice; **LFU** (least frequently used) suits workloads with a stable set of very hot keys.

## Problems caches cause

- **Stale data.** A missed invalidation shows old data until the TTL runs out. Keep TTLs as a safety net.
- **Stampede.** A hot key expires and thousands of requests miss together and flood the database. Fixes: let one request rebuild the value (a short lock), serve the old value while it rebuilds, or add random jitter to TTLs so keys don't expire together.
- **Hot keys.** One key, such as the live score of a cricket final, gets more traffic than one cache node can serve. Copy it to several nodes or keep a tiny in-process cache on each app server for a second or two.
- **Cold start.** An empty cache after a restart sends all traffic to the database. Warm the most important keys first.

## What interviewers look for

- **A reason to cache.** The read-to-write ratio and the latency you are saving, from your estimates.
- **Placement.** CDN for static files and the app cache for queries, with the CDN mentioned early for anything media-heavy.
- **A clear write path.** What happens to the cache when data changes, and why that choice.
- **Failure thinking.** Stampedes, hot keys and what happens if the cache cluster goes down.

## Common mistakes

- **Caching everything** without a hit-rate goal. A cache with a 20% hit rate adds a network hop for little gain.
- **Treating the cache as the source of truth.** It can be emptied at any time; the database must still hold the data.
- **No TTLs**, so one missed invalidation means stale data forever.
- **Caching per-user data with a shared key**, so one user sees another's data. Include the user ID in the key.
