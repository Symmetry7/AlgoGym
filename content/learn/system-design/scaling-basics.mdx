## The idea

When traffic grows past what one machine can serve, you have two moves:

- **Scale up (vertical):** a bigger machine, with more CPU, memory or faster disks. No code changes.
- **Scale out (horizontal):** more machines doing the same job, with a load balancer in front to share the work.

Most real systems do both: scale up until it gets expensive or risky, then scale out. Interviewers want to hear that you know the limits of each.

## Scaling up

Moving from 4 cores and 16 GB to 32 cores and 256 GB is a few clicks on any cloud provider. It is the right first answer for a young product, and it is the usual answer for a database, which is much harder to split than an app server.

Its limits:

- **A ceiling.** The largest machines are finite, and the price per core climbs steeply near the top.
- **A single point of failure.** One machine means one crash, one bad deploy or one hardware fault takes everything down.
- **Downtime to resize.** Moving to a bigger machine usually means a restart.

## Scaling out

Add identical servers and put a load balancer in front. Capacity grows roughly in line with the number of servers, and losing one server costs a third of your capacity instead of all of it.

The catch is **state**. If server 1 keeps a user's login session in its own memory, a request that lands on server 2 doesn't know who the user is. The fix is to make app servers **stateless**: anything that must outlive a single request goes to a shared place.

- Sessions go to a shared store such as Redis, or into a signed token (for example a JWT) that the client sends with every request.
- Uploaded files go to object storage, not the server's local disk.
- Scheduled jobs run once, from a queue or a scheduler, not on every server.

Once servers are stateless, any of them can handle any request, and adding the fourth or the fortieth is routine. The database then becomes the hard part. Later lessons cover how caching, replicas and sharding take load off it.

## Numbers to know

Design decisions follow from where time goes. These are order-of-magnitude figures, which is all an interview needs:

| Operation | Rough time |
| --- | --- |
| Read from main memory | about 100 ns |
| Read 1 MB sequentially from memory | a few µs |
| Random read from an SSD | about 100 µs |
| Network round trip inside one data centre | about 0.5 ms |
| Redis GET over the network | under 1 ms |
| Simple indexed database query | 1 to 10 ms |
| Round trip Mumbai to Delhi | about 30 ms |
| Round trip India to the US east coast | about 200 ms |

Two conclusions worth saying out loud: memory is about a thousand times faster than an SSD, which is why caches work; and the speed of light makes cross-continent calls slow, which is why CDNs and regional servers exist.

## What interviewers look for

- **A sensible order.** Start with one server, scale up while it's cheap, scale out when you need redundancy or more capacity than one box gives.
- **Stateless app servers.** You notice session and file state and move it somewhere shared before adding servers.
- **The database as the next bottleneck.** You don't stop at "add more servers": you say what happens to the database when there are 20 of them.
- **Latency awareness.** You can say roughly how long a memory read, a disk read and a network hop take, and use that to justify a cache or a region.

## Common mistakes

- **"Just add more servers"** without mentioning the load balancer, session state or the shared database behind them.
- **Treating the database like an app server.** Copying a database is not the same as adding a stateless server; writes must still agree.
- **Forgetting failure.** Horizontal scaling is as much about surviving a dead machine as about throughput. Say both.
