## The idea

Replicas spread reads, but every write still lands on one primary, and one machine has a limit on disk, memory and write throughput. **Sharding** (horizontal partitioning) splits the rows of a table across several databases. Each shard holds part of the data and takes part of the writes.

It is powerful and expensive: cross-shard queries, rebalancing and operations all get harder. In an interview, reach for it when your estimates say one primary can't keep up, and say why.

## Choosing the shard key

The shard key decides which shard owns a row. A good key:

- **Matches the main access pattern**, so common queries hit one shard. For a chat app, `conversation_id`; for a store's orders, often `user_id`.
- **Spreads load evenly.** Many distinct values, none dominating.
- **Doesn't change.** Moving a row between shards because its key changed is painful.

## Hash or range

| Split | How | Strength | Weakness |
| --- | --- | --- | --- |
| Hash | hash(key) picks the shard | Even spread of data and writes | Range queries ("orders from last week") hit every shard |
| Range | Key ranges, such as A to F | Range scans stay on one shard | Hot spots when new keys cluster (time, sequential IDs) |
| Directory | A lookup table maps each key or tenant to a shard | Full control, easy to move one big customer | The lookup service must be fast and highly available |

**Rebalancing.** With `hash(key) mod N`, adding a shard changes N and remaps most keys. Two standard fixes: **consistent hashing**, where a new shard takes over only its arc of the ring, and **many fixed partitions** (say 1,024) mapped onto a few machines, so growing means moving whole partitions, not rehashing rows.

## Hot shards

Even a good key can concentrate load. A celebrity's account, a viral post or one enterprise tenant can make one shard far busier than the rest. Options: split that key further (append a suffix and spread its rows over several shards, merging on read), give the tenant a dedicated shard, or cache its reads aggressively.

## What you give up

- **Cross-shard joins.** Join in the application, or denormalise: store the data you need together on the same shard.
- **Cross-shard transactions.** Keep each transaction inside one shard by choosing the key well; otherwise you need patterns such as sagas, covered in the queues lesson.
- **Global uniqueness and IDs.** Auto-increment per shard collides. Use IDs that are unique without coordination: UUIDs, or time-ordered IDs that combine a timestamp, a machine number and a counter.
- **Operational simplicity.** Backups, schema changes and monitoring now happen N times.

## What interviewers look for

- **Sharding when the numbers demand it**, after indexes, caching and replicas.
- **A shard key tied to the queries**, with the reason in one sentence.
- **Awareness of hot keys** and how to rebalance without moving everything.
- **Honest costs**: what happens to joins, transactions and IDs.

## Common mistakes

- **Sharding at the start** of the design, for a load one database handles easily.
- **Sharding by a time or sequential key**, which sends every new write to one shard.
- **Forgetting the read path**: a key that is perfect for writes but makes the main query scatter to every shard.
- **`mod N` with no rebalancing plan.**
