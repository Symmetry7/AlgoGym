## The idea

Binary search finds a **boundary**: the first place where a yes/no question changes from "no" to "yes". Look at the middle of the range, answer the question there, and throw away the half that can't contain the boundary. Each step halves the range, so n candidates need about log₂ n steps.

The question doesn't have to be "is this value in the array". It can be "is `departures[mid] ≥ arrival`?", or, without any array at all, "can the shop finish in time with capacity `c`?"

Finding a word in a printed dictionary works the same way. You open it in the middle, see that "mango" comes after "kettle", and never look at the first half again. A few more halvings and you're on the right page.

## Worked example

*First Departure* asks for the first train at or after minute `560` in `[540, 555, 570, 600, 630]`.

Keep `lo = 0` and `hi = 5`, so the answer is somewhere in `[lo, hi)`. The middle is index 2, time 570. That's not too early, so the answer is index 2 or before it: `hi = 2`. The middle of `[0, 2)` is index 1, time 555, which is too early, so `lo = 2`. Now `lo == hi == 2` and the range holds exactly one candidate: **index 2**. Three comparisons instead of scanning the list.

*Square Plot* and *Ration Counter* use the same loop on a range of answers instead of an array. *Rotated Timetable* adds one twist: first work out which half is still sorted.

## Code

<CodeTabs>

```js
function lowerBound(values, target) {
  let lo = 0;
  let hi = values.length;
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (values[mid] < target) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}
```

```python
def lower_bound(values: list[int], target: int) -> int:
    lo, hi = 0, len(values)
    while lo < hi:
        mid = (lo + hi) // 2
        if values[mid] < target:
            lo = mid + 1
        else:
            hi = mid
    return lo
```

int lowerBound(const vector<int>& values, int target) {
    int lo = 0, hi = values.size();

        else hi = mid;
    }
    return lo;
}

## Complexity

| | |
| --- | --- |
| Time | O(log n) comparisons; O(log R × cost of the check) when searching a range of R answers |
| Space | O(1) |

## Common mistakes

<Callout>

- **Mixing range styles.** With `[lo, hi)` use `lo < hi` and `hi = mid`. With `[lo, hi]` use `lo <= hi` and `hi = mid − 1`. Mixing them loops forever or skips the answer.
- **`lo = mid` with `mid` rounded down.** When `hi = lo + 1`, `mid` stays at `lo` and the loop never ends. Round up, as in `(lo + hi + 1) / 2`, whenever you write `lo = mid`.
- **Overflow.** `(lo + hi) / 2` and `mid × mid` can overflow 32-bit integers. Use `lo + (hi − lo) / 2` and 64-bit products.

</Callout>
